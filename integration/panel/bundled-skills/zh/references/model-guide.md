# 模型画像、档位经济学与审稿清单

## 一、角色能力画像

| 维度 | `codex-gpt-6.2-sol-high` | `codex-gpt-6.2-astra-high` | `gemini-4-neon-xhigh` | `gemini-4-hydrogen-xhigh` |
| :--- | :--- | :--- | :--- | :--- |
| **核心定位** | 默认主力执行者 | 默认深度审查与攻坚者 | 主控统筹、规划裁决、审美与重要文档负责人 | **临时落实兜底**（非持久） |
| **强项** | 多文件并行落地、补齐单测与回归、运维脚本、仿真与建模代码 | 跨层不变量、并发/状态机排障、数学推导、独立终审 | 全局取舍、剔除过度防御、UI/3D 视觉品味、清晰文档与文案 | 接替 Sol 卡壳/受阻的局部实现切片 |
| **短板与禁区** | 不适合架构拍板与视觉设计；**写文档带防御套话，禁改重要文档与文案** | 易过度防御、放大边缘风险并给重型方案；同样**禁改重要文档与文案** | 上下文与配额宝贵，避免亲干脏活 | 仅限落实兜底，**完成后即关闭**，不持久化也不担统筹/文档/审美 |
| **上下文与缓存** | 1M 上下文；稳定公共前缀下实测缓存命中可达 90%–97% | 同为 1M 上下文；稳定前缀同样高命中，长推演需留输出空间 | 负责轻量高频调度与关键文档 | 临时切片短平快交付 |
| **相对配额成本** | 约 1×（主力池） | 约 4×（聚焦高价值疑点） | 稀缺，保持轻量 | 共享 Gemini 配额，严格按需临时调用 |

> **Claude 政策**：Claude 额度极少，**默认一律不使用**，仅在用户明确授权时启用。

## 二、默认档位与性价比曲线

- **Sol 与 Astra 统一从 `high` 起步**：`low`/`medium` 在真实工程中极易漏掉隐含契约或引入返工，返工成本反而高于直接跑 `high`，不考虑低于 `high` 的档位。
- **Neon 统一默认 `gemini-4-neon-xhigh`**：`xhigh` 是 Neon 统筹裁决、审美品味与文档质量的最优档位，主控、规划员与文案/视觉把关均直接使用 `xhigh`。
- **`high` 是性价比拐点**：公开基准（如 Artificial Analysis）与项目实测均显示，从 `high` 升到 `xhigh`/`max` 的能力增益明显收窄（示意：Astra `high` 约 60 → `max` 约 62），但延迟与推理 token 开销往往放大 2–4×，`max` 单任务耗时甚至达数分钟至十几分钟。
- **何时向上升级**：
  - `astra-high → astra-xhigh`：仅在遇到高风险有状态系统审计、疑难并发根因、硬核数学证明，或 `high` 连续两次未收敛时启用；派发时只给单一未解问题与复现证据。
  - `astra-xhigh → max`：极罕见封顶手段，仅用于高损失且证据冲突的单点复核，必须设明确截止与退出条件，严禁给并行执行者使用。
  - **难题一旦解开，立刻把实现与回归交回 `sol-high`。**

## 三、文档与文案分工红线

GPT-6.2 在撰写面向人的文档和文案时，习惯堆砌免责声明、过度限定词和防御性套话，严重削弱表达清晰度与专业质感。协作中严格分层：

- **允许 GPT 写的内容**：
  - 运行日志、基准测试原始输出、故障复现记录；
  - 单次改动的局部变更清单（改了哪些文件、跑了哪些命令、结果是什么）；
  - 面向主控的精炼只读审查条目（供 Neon 裁决，不直接面向最终读者）。
- **必须由 `Neon` 掌控的内容**：
  - **重要文档**：`README`、架构设计文档、ADR、项目规范、Skill / Rule 指令文件、对外发布说明（由统筹者统一维护或派 Neon 成员起草）；
  - **所有文案处理**：产品文案、UI 提示语、错误文案润色、报告与总结定稿。

## 四、反过度防御：六条审稿清单

实测中即使 Astra 的 P0/P1 命中率很高，仍常混入 15%–25% 低收益建议，以及约 1/3 过度厚重的改造方案。审稿时按以下六条逐项过滤：

1. **只认复现，不认臆测。** 要求给出失败测试、复现步骤或明确不变量推导；没有证据的假设性担忧不作为阻塞项。
2. **事实与方案拆开裁决。** 可以采纳缺陷本身，同时否决重型方案——局部 Bug 不默认引入新抽象层、状态机、独立账本或线程池。
3. **守住既有契约与兼容。** 凡可能破坏既有契约测试、序列化格式或下游行为的建议，未经主控拍板一律驳回。
4. **优先最小充分修复。** 同类低收益 P2 合并或延后；优先用轻量手段解决问题（如事务内校验、有界重试、轻量就绪信号），别用重架构代替局部修补。
5. **重点复核并发与资源回归。** 对并发优化与批处理改动，重点检查旧响应反序覆盖、峰值内存暴涨、身份漂移与失败回滚。
6. **落盘裁决理由。** 每条清晰标注 `采纳 / 裁剪 / 驳回` 及一句理由，防止后续成员反复纠缠已决事项。

## 五、运行期注意与临时兜底

- **原生模态**：当前 GPT 通道只原生支持 `text` + `image`，不支持原生 PDF；遇 PDF 先用脚本提取文本或渲染关键页图片再传入。
- **视觉验收**：前端 UI 与 3D 场景必须由 Neon 审查真实浏览器截图或多视角渲染图；功能测试全绿不能替代视觉把关。
- **Sol 无法落实时的临时接替**：当 `sol-high` 因误拒、连续卡死或通道异常无法完成某个具体实现切片时，由主控保存现有补丁和精确交接上下文（基线、白名单、契约、已跑命令），临时派发 **`gemini-4-hydrogen-xhigh`** 完成该切片的落实与验证；**交付后立即关闭/回收该 Hydrogen 成员，不留作常驻**。
- **保持单写主责**：任何接替或重试前先移交写入权，绝不让两名成员同时修改同一写集。
